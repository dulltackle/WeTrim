# 长文采用连续渲染，不做虚拟列表

清洗界面按 A 单栏连续阅读一次性渲染全部内容块，不实现虚拟列表，也不实现分段延迟呈现。依据是一次可丢弃探针的实测：在 4× CPU 降速的低端设备代理下，300 块 / 1.87 万字 / 30 图的文章挂载耗时 670 ms，600 块 / 3.72 万字 / 60 图为 850 ms；滚完全篇每步 p95 为 34 ms，未观察到掉帧；内存由图片解码主导且随规模饱和，块数与图片数翻倍只多约 21 MB。而微信公众号正文的平台上界约在 2 万字量级，也就是说连续渲染在这个产品能遇到的最大文章上仍有数倍余量。虚拟化在此没有可证明的收益。

代价是这一选择会随文章规模失效，因此架构上保留一处接缝：全部块的渲染入口收敛到单一的块列表组件边界。真正的风险不在渲染本身而在耦合——[清洗界面契约](https://github.com/dulltackle/WeTrim/issues/9#issuecomment-5594805365)要求操作后保持阅读位置与键盘焦点，若搜索定位和焦点管理直接操作 DOM 并假设"每个块都在文档里"，将来任何虚拟化都会同时打碎这三件事。因此搜索、序号定位与焦点管理必须经由块列表组件的接口，不得绕过它访问 DOM。

同一批测量还支持两项相关取舍：会话按单个 key 整篇序列化保存而不分块（600 块整篇序列化加写入仅数毫秒），以及每块常驻原始 HTML、初始 Markdown 与当前编辑三份文本而不削减（600 块整份载荷 473 KB，JS 堆个位数 MB，与图片解码的约 200 MB 差三个数量级）。

**2026-09-11 更正**：本文写作时按「平台上界约 300 块」估算余量，据此说「仍有数倍余量」。[真实长文样例](https://github.com/dulltackle/WeTrim/issues/12#issuecomment-5602467069)实测文字密集长文为 35 字/块（合成样例是 62 字/块），2 万字上界因此对应**约 600 块**而非 300 块。渲染决策本身不变——580 块落在已实测的 600 块档内（挂载 850 ms @4×，目标 1.5 s）——但余量是约 1.8 倍，不是「数倍」。
