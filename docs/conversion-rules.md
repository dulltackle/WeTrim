# 微信 HTML → Markdown 转换规则清单

[`ARCHITECTURE.md`](../ARCHITECTURE.md) 的附录。写转换器时摊开在旁边逐条对照用。

架构约束在 `ARCHITECTURE.md` §6 与 [ADR-0007](./adr/0007-per-block-conversion.md)：**每个内容块独立转换，绝不整篇拼接后回填占位符**。本清单的每一条都默认在这个前提下执行。

切块边界的**产品定义**在 [ADR-0001](./adr/0001-content-block-boundaries.md) 与 [#5](https://github.com/dulltackle/WeTrim/issues/5#issuecomment-5581555371)；本文档讲的是**怎么在真实的微信 DOM 上实现它**。

### 证据等级

每条规则标注它的依据强度。这个标注是规则的一部分，不是修饰：

| 标记 | 含义 |
| --- | --- |
| ✅ **实测** | 有真实文章样本支持，样本数标在括号里 |
| 🔧 **构造** | 只用手工构造的 HTML 验证过，**不是真实形态的证据** |
| ⚠️ **未验证** | 只有推断或上游经验，本项目没有任何样本 |

## 1. 通用原则

1. **未知标签去标签留内容。** `section`、`span` 和一切不认识的标签，丢掉标签本身、保留子内容。Turndown 的默认行为就是这样，因此**不需要写任何「拍平嵌套 section」的代码**——上游靠 markdownify 的同一默认行为达成了同样效果（✅ 上游源码全文无拍平逻辑）。
2. **编辑器标记透明处理。** `<span leaf="">`、`<span textstyle="">` 是微信编辑器的标记，没有语义，当透明容器处理。✅ 实测（4 篇）。
3. **行内格式必须保留。** `<strong>`、`<em>`、`<a>`、`<code>` 等照常转换，不能因为外层是列表或引用就丢掉。✅ 实测（4 篇，47 处行内代码全部正确并入所在块）。
4. **标签名解析要允许 `:`。** 微信文章里会出现从 Word 粘贴来的命名空间标签。✅ 实测遇到 `<o:p>`（#12）。用 `DOMParser` 时浏览器原生处理；但任何自写的标签名匹配（正则、判据）都必须允许冒号，否则这类标签会被当作文本泄漏成一个**假段落块**。
5. **所有生成的内容块初始 `included = true`。** 内容由用户手动清洗，转换器不替用户做取舍判断（[#5](https://github.com/dulltackle/WeTrim/issues/5#issuecomment-5581555371)）。

## 2. 正文与元数据的定位

| 目标 | 选择器 | 证据 |
| --- | --- | --- |
| 正文容器 | `#js_content` | ✅ 上游 + 本项目 10 篇 |
| 标题 | `#activity-name` | ✅ 同上 |
| 公众号名 | `#js_name` | ✅ 同上 |

**发布时间**藏在页面的内联 `<script>` 变量 `create_time` 里，解析要处理三种格式：`JsDecode("…")`、纯数字、`k=v` 赋值。

四个必须照抄的防御（✅ 上游踩过的坑，是微信平台的数据格式，不是 Python 实现细节）：

1. **按位数区分秒与毫秒**；
2. **先解码 HTML 实体**再解析；
3. **值可能已经是日期字符串**，不一定是时间戳；
4. **时区硬编码 UTC+8**，不用运行环境时区——否则导出时会随导出设备时区跨日。

无法可靠解析时 `publishedAt = null`，front-matter 省略 `date` 字段，**不输出空占位**。

> 注意：上游输出的**不是** YAML front-matter，而是纯 Markdown 头 + blockquote。本项目的四字段 front-matter 是 [#6](https://github.com/dulltackle/WeTrim/issues/6#issuecomment-5581985012) 的产品决定，不是上游既有输出，不要照搬。

## 3. 噪声清单

**不成块**（这些不是正文内容）：

| 选择器 | 理由 | 证据 |
| --- | --- | --- |
| `script` | — | ✅ 上游 |
| `style` | — | ✅ 上游 |
| `pre[class*="js_darkmode"]` 且无文本 | 暗黑模式样式载体，不在 `.code-snippet__fix` 内。上游没处理它，一篇 40 个代码块的文章因此转出了 **19 个空代码围栏** | ✅ 上游 PR #13 的真实案例 |
| `.qr_code_pc` | 二维码 / PC 引导 | ⚠️ 上游删了它，但本项目**没有真实样本**确认它出现在 `#js_content` **内**。实现期确认真实形态 |
| `.reward_area` | 赞赏区 | ⚠️ 同上 |

**明确不是噪声，不得删除**：

- **公众号名片、小程序卡片等富媒体**。它们是正文内容，见 §4.10。把它们当噪声是 [#5](https://github.com/dulltackle/WeTrim/issues/5#issuecomment-5581555371) 点名过的错误。
- **代码块的行号 `<ul>`**。它不是内容列表，但也不能独立删——它随所属代码块一起处理，见 §4.4。

**上游没有处理、我们也不主动处理的**：「关注引导」「留言区」。上游源码与全部 13 个 issue/PR 里都找不到对应选择器，推测它们在 `#js_content` **之外**，天然不会被带进来（⚠️ 推断，未实测）。

## 4. 切块与逐类转换

### 4.0 穿透判据（最容易写错的一条）

从正文 DOM 按原顺序切块。先识别**完整语义单元**，再穿透排版容器。

> **穿透判据必须是「有块级后代 _或有完整语义单元后代_ 就继续穿透」。**

**不能**用「无块级后代 = 叶子内容」。✅ [#12](https://github.com/dulltackle/WeTrim/issues/12#issuecomment-5602467069) 实测：图集那篇的公众号卡片结构是 `section.mp_profile_iframe_wrp > mp-common-profile`，外层 `section` 不含任何块级标签，于是被当成叶子走行内展开，而行内展开只收文本与图片——**整张卡片静默消失**。卡片没有文本节点，也没有 `img` 子节点，全部内容在属性里。

`hasUnitDescendant` 这个判据在 4 篇真实样例的 6 处卡片上全部正确（✅ #13）。

两条配套规则：

- **穿透时保留直接文本节点**，不能只遍历子元素。
- **已识别的完整语义单元优先于容器标签判断**——不能因为代码块或富媒体也用 `section` 就把它们拆散。

### 4.1 完整语义单元一旦成块，内部不再产生独立块

列表、引用、表格、代码各自整体成一个块。引用套列表 → 一个**引用块**；列表套引用 → 一个**列表块**；嵌套列表 → 归外层列表。

内部的图片没有独立取舍开关，用户通过编辑该块的 Markdown 删改。

✅ 4 篇真实样例中所有结构的切块行为全部符合 ADR-0001（#13）。

### 4.2 段落与行内

- 普通段落中的「文字 A → 图片 → 文字 B」**切成三个块**；仅包裹图片的段落成为**图片块**。
- 拆分时保留文字片段中的行内格式与链接，**不因 `span` 或行内换行另切块**。
- **标题等已识别的完整单元不套用这条图片拆分规则。**
- 行内公式留在所属文字内容里（见 §4.9）。

### 4.3 标题

保留层级，转成对应级数的 Markdown 标题。`headingLevel` 存进 `Block`。

### 4.4 代码块：两种形态，行号与换行的编码方式**正好相反**

这是整份清单里最容易出错的一节。上游只处理了官方形态，真实文章里另有一种第三方排版工具产出的形态。

| | 官方 `.code-snippet__fix` | 第三方 `pre > code` |
| --- | --- | --- |
| 语言 | `pre[data-lang]`，**但可能是空串** | **无 `data-lang`，语言丢失** |
| 行号 | 隔离在 `<ul class="code-snippet__line-index">`，删掉即可 | **内联在代码文本里** |
| 行号判据 | class 明确 | **只有内联样式 `user-select: none`**（该形态完全没有 class） |
| 换行 | **一行一个 `<code>`**，`<br>` 数为 **0** | **靠 `<br>`** |
| 证据 | ✅ 8 个真实代码块（两轮独立复证） | ✅ 1 个真实代码块 |

**两种形态的 `textContent` 都是错的：**

- 官方形态会把相邻行**首尾相连**：`# Loop：串行，每个审查等上一个完成def agent_loop(task):`（注释行和 `def` 行粘住）。→ **必须按 `<code>` 边界补 `\n`。**
- 第三方形态每行开头**多一个行号**：`1def tolerance_reverse_check(...):2  valid_min = ...`；更糟的是**空行会让两个行号连成一个数**（第 4、5 行 → `45`）。→ **必须按内联样式识别并剔除行号节点。**

**三条硬规则：**

1. **`data-lang` 取值必须判空，空串按无语言处理。** ✅ 8 个官方代码块里有 **2 个是空字符串**（都是单行代码块）。
2. **`li` 数 === `code` 数。** ✅ 两轮 8 个代码块全部成立（27=27、21=21、9=9、1=1、1=1、11=11、15=15、24=24）。这条可以当硬规则，用作转换后的自检——不相等说明行号剔除或换行切分出了问题。
3. **两种形态的缩进都是 `&nbsp;`（U+00A0），写进围栏前必须替换成普通空格。** ✅ 实测 71 / 126 个。不替换的话缩进在渲染和再编辑时都会坏。

**还要跳过 CSS `counter(line…)` 泄漏的垃圾行**（✅ 上游）。判据用清晰的字符串前缀（`text.trim().startsWith('counter(line')` 一类）即可，不必照抄上游那个 `^[ce]?ounter\(line` 的 hack。

### 4.5 列表

真实形态（✅ 4 篇，12 个内容列表）：

```html
<ul class="list-paddingleft-1">
  <li><p style="…"><strong>…</strong><span leaf="">…</span></p></li>
</ul>
```

```html
<ol class="list-paddingleft-1" style="list-style-type: decimal;">
  <li><p style="…"><span style="…"><span><span style="…">应用执行下线脚本…</span></span></span></p></li>
</ol>
```

- **有序与无序完全同构**，除标签名和 `list-style-type: decimal` 外一模一样。✅ 3 个真实有序列表。
- **`<li>` 里包着 `<p>`。** 转 Markdown 时 `- ` / `1. ` 后面要接 `<p>` 的**行内内容**——当成独立段落会多出空行、破坏列表。✅ 实测。
- **`start` 属性**：3 个真实有序列表**都没有** `start`，编号都从 1 开始。实现仍应尊重 `start`，只是真实文章里没出现过。
- **代码块的行号 `<ul>` 不是内容列表。** ✅ #13 第二轮那篇 12 个 `ul` 里有 **7 个是行号容器**。统计和切块都要排除它们。

#### 嵌套列表：两种编码假设实测确认与统一合并

微信多级列表编码的实现期实测结论（✅ #20）：

1. **微信官方多级列表采用真嵌套 `<ul><li><ul>`（假设 A）**：实测确认微信官方渲染白名单（`list-paddingleft-1, list-paddingleft-2, list-paddingleft-3`）与真实多级列表文章，其原生编辑器生成的多级列表是真嵌套结构；
2. **平铺兄弟 + `list-paddingleft-N`（假设 B）**：常见于第三方微信排版工具或富文本从外部编辑器（如 Word/UEditor）复制粘贴产生的形态。

WeTrim 对两种假设完整支持并实测验证：

| 构造 | 切块策略 | 切块结果 | 符合 ADR-0001 |
| --- | --- | --- | --- |
| **假设 A**：真嵌套 `<ul><li><ul>` | 原生识别为单一语义单元 | 三级内容整体成 **1** 个列表块 | ✅ |
| **假设 B**：平铺兄弟 + `list-paddingleft-N` | **在切块前合并相邻兄弟列表**（中间无其它内容），把 `paddingleft-N` 当缩进层级重构为嵌套树 | 同样整体成 **1** 个列表块 | ✅ |

> **合并策略的固有降级**（✅ 已在 #20 验收记录）：作者真的连写两个独立一级列表、中间不隔内容时，在平铺编码下与「一个列表」在 DOM 里无法区分——微信自己渲染也完全一样。合并是两害相权的最佳决策。


### 4.6 引用

整段 `blockquote` 成一个**引用块**。

- ✅ 5 个真实引用，**全部是单段落形态**。行内格式（粗体、斜体、行内代码、带参数链接与相对链接）与图片完整随块保留。
- 🔧 **多段落引用与引用套列表无真实样本**，只能用手工构造 HTML 验证（见 `test/fixtures/constructed-quotes.json` 与 #21）：
  - 多段落引用段落间正确保留 `> ` 前缀，整体成 1 个引用块，段落间空行不产生独立块或丢失前缀；
  - 引用套列表整体成 **1** 个引用块（🔧 构造验证），内部列表（包括有序、无序、真嵌套树及平铺兄弟列表合并）在引用内正确缩进（符合 ADR-0001）；
  - 引用内部的图片随块呈现，在 Markdown 中正常输出，不产生独立的图片块，同时正常收集至 `ImageAsset` 清单供导出下载。

### 4.7 表格

整张表成一个**表格块**。✅ #12 实测 19 + 2 个真实表格，215 个 `td`。

- 能按普通行列表示的 → GFM 管道表格（`turndown-plugin-gfm`）。
- 存在无法可靠表达的**合并单元格或复杂嵌套**时 → 按行、单元格顺序**降级为可读文本**，保留可取得的文字、链接与图片引用，并挂一条 `code: 'table-degraded'` 的**转换提示**。
- **不以原始 HTML 作为保真兜底。**

### 4.8 图片

- **`data-src` 优先于 `src`。** 只在 `data-src` 有值时才用它，否则退回 `src`。✅ 上游 + #4（27 张图的真实地址全在 `mmbiz.qpic.cn`）。
- **不需要模拟滚动。** 微信在页面加载时就把真实地址预写进 `data-src`，不是滚动触发。✅ #4 三篇：滚动前后的标签、文本事件、真实图址与顺序完全一致。
- **URL 原样保留，包括全部查询参数。** 不清洗、不归一化微信的尺寸、格式或签名参数。
- **`wx_fmt` 只用来猜扩展名**，不用来改 URL。且导出时**以实际媒体格式为准**，`wx_fmt` 只是候选（见 `PRODUCT.md` 的导出小节）。
- **按完整 URL 字符串去重**，不做内容哈希。上游的 MD5 去重来自未合并 PR #7，是「跨文章共享图片」场景才需要的，与本项目 Out of scope 一致。
- 相对地址以来源文章 URL 解析为绝对地址。

### 4.9 公式

- **行内公式留在所属文字块里；只有独占一行的才单独成块。**
- ⚠️ **这条已知会被写错。** #13 的切块器对**任何**公式元素都返回「独立公式」，结果 `行内公式 <mjx-container/> 之后。` 被切成三块（段落 / 独立公式 / 段落），**句子被劈开**。
- 判据参考「父级是否只有它一个有内容的孩子」（#13 的 `isBlockLevelFormula`）。
- ⚠️ **无真实公式样例。** 探测目标是 MathJax / KaTeX / `math` 一类元素（如 `mjx-container`），但微信实际用哪种渲染方式**没有样本**。若公式是图片（LaTeX 截图），走图片块的通用逻辑。
- 输出方言：行内 `$…$`，独立 `$$…$$`。

### 4.10 富媒体

**内容全部在属性里**，这是它最容易被丢掉的原因。✅ 4 篇实测 6 处，全部正确：

| 元素 | 内容位置 |
| --- | --- |
| `mp-common-profile` | 昵称、简介、头像在属性里；**没有文本节点，也没有 `img` 子节点** |
| `mp-common-miniprogram` | `data-miniprogram-title` 等属性 |

常见包装：`section.mp_profile_iframe_wrp > mp-common-profile`。

转换规则：

- 尽可能保留**名称、可读文字和有效链接**。
- 无法完整表达的用可读占位：`【视频】名称`、`【小程序】名称`、`【公众号】名称`，有链接时用 Markdown 链接表达。
- 挂一条 `code: 'richmedia-placeholder'` 的**转换提示**。
- **没有名称或地址就说明原内容的类别。不伪造信息，不用空字符串掩盖内容丢失，也不承诺原样复现。**

### 4.11 未知内容

无法识别类别的内容 → **未知内容块**，以可读信息或占位说明呈现，供用户决定保留或剔除。

**普通的行内包装标签不因此变成未知块**——它们按 §1.1 去标签留内容。

转换抛错或「原始 HTML 非空却转出空内容」的块也降级到这里，见 `ARCHITECTURE.md` §6.2。

### 4.12 分割线

`<hr>` → `---`。✅ #4 的一篇里有 6 个。

## 5. 转换后的自检

这些检查在实现期很便宜，能挡住整类静默故障：

| 检查 | 挡住什么 |
| --- | --- |
| 官方代码块的 `li` 数 === `code` 数 | 行号剔除或换行切分出错 |
| 块的 `originalHtml` 非空但 `initialMarkdown` 为空 | 富媒体卡片一类的静默丢失（`ARCHITECTURE.md` §6.2 的第二条触发条件） |
| 围栏代码块内不含 U+00A0 | 忘了替换 `&nbsp;` 缩进 |
| 列表块的 Markdown 不含多余空行 | `li > p` 被当成独立段落 |
| 没有内容为纯数字的孤立段落块 | 第三方代码块的行号泄漏成正文 |
